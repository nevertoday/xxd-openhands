## 先看一对

这样说，它只能猜：

```text
帮我修一下代码里的 bug。
```

这样说，它直接知道去哪、修成什么样：

<Copy id="gi-good" title="写清楚的版本" code={`修好 src/api/users.py 第 45 行的 TypeError。
报错原文：
TypeError: 'NoneType' object has no attribute 'get'
应该怎样：用户没存过偏好时，get_user_preferences() 返回默认偏好。
实际怎样：user.preferences 是 None 时，直接报上面的错。
做好的样子：这种情况返回 DEFAULT_PREFERENCES，测试都通过。
做完给我看：改了什么，和测试结果。`} />

差别在于：有文件和行号，有原样的报错，有应该怎样和实际怎样，还说了怎么算修好。

## 写清四样东西

- **在哪。** 文件、行号、函数名。不知道就说是哪个功能。
- **现在怎样，应该怎样。** 原样贴报错和日志，别转述。
- **背景和不能碰的。** 谁在用、出错有多严重、哪些接口不能变、照哪里的写法来。
- **怎么算做完。** 最好能用命令检查：哪些测试要过、哪个接口返回什么。

<mark>「怎么算做完」最要紧。</mark>官方文档说，目标越能用程序检查，它做得越好。没有这样的检查，给一张要做完的清单也行。

| 别说 | 要说 |
| --- | --- |
| 修一下报错 | 修 api.py 第 45 行的 TypeError |
| 加点测试 | 给 calculateTotal 补边界情况的单元测试 |
| 提升性能 | 把 N+1 查询改成一次 join |
| 整理一下代码 | 把校验逻辑抽成一个 ValidatorService |

## 一次只交代一件事

官方建议一个提示词只做一个功能，改动一般不超过 100 行。大活拆成几步，一步一个提示词。比如换登录方式，可以分三次：

<Copy id="gi-phase" title="第一步：先只做分析" code={`分析现在的登录系统，列出迁移到 OAuth2 要改动的所有地方。
做好的样子：每一处写清文件和它在登录流程里的作用。
做完给我看：这份清单。这一步先不改代码。`} />

第二步再让它加上 OAuth2 的配置和基本流程，旧的登录照常能用。第三步再把用户登录切过去，保持向后兼容。

## 照这个格式写

复杂的任务，套这个格式：

<Copy id="gi-template" title="任务模板" code={`## 任务
<一句话说要做什么>

## 背景
<为什么要做，这段代码是做什么的、谁在用>

## 要求
1. <具体要求>
2. <具体要求>

## 不能碰的
- <不能改的接口、文件、行为>

## 怎么算做完
- <哪些测试要过，用什么命令检查>

## 做完给我看
- <改了什么、测试结果、截图或输出>`} />

能给例子就给例子。比如想要的报错格式，直接贴一段给它看。

## 这几种说法，它最容易跑偏

- **「弄好看点」**：好不好看没有标准。写清要改成什么样，或者给一张参考图。
- **「看看哪里不对」**：太含糊。给出现象、报错和你已经排除的原因。
- **「全部重写」**：太大。先挑一块，一次做一块。
- **「你看着办」**：它不知道你要什么。写清要求。
- **没人审就改线上的基础设施**：先让人审过。

还有几类事，官方建议你自己多拿主意。比如要靠团队内部经验才知道的事，主观的视觉设计，和一点错都不能出的代码。

## 发出去才发现说错了

- **先让它停下。** 点输入框旁的「Stop」。
- **改了再重发。** 在你那条消息上点「Branch from here」。原话会出现在输入框里，改好再发。原来的对话还在。
- **它做到一半挺好，想换个下一步。** 在它的那条回复上点「Branch from here」，新对话从那里接着。

分叉要本机的 <Term k="Agent Server" /> 后端，而且它支持对话分叉。没有这个按钮，就开一个新<Term k="对话" />，把前面的结论写进第一句。

## 每次都要说的话，写进 AGENTS.md

同一句交代说了第二遍，就把它写进项目根目录的 <Term k="AGENTS.md" />。每个对话开始时都会读它：

```markdown
## OpenHands 要知道的事

- 新加 API 接口时，一定要加到 routes/index.js
- 日期一律用 ISO 8601 格式
- 所有数据库查询都走 repository 那一层
```

## 卡住了？

<Q q="它先问了一堆问题，才肯动手。">
这是正常的。回答完它的问题，再让它开始。下次把这些写进第一句，它就不用问了。
</Q>
<Q q="它改的比我要的多得多。">
把范围写死：「只改这一个文件」「不要动别的功能」。官方把「时间和范围的限制」列为要写清的要求之一。
</Q>
<Q q="它总是不知道项目的规矩。">
它不记得上一次对话。把规矩写进 AGENTS.md，每个对话都会读到。
</Q>
