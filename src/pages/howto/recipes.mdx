尖括号里的换成你自己的：文件、报错、怎么算做完。每一句都按同一个顺序写：我想要什么、做好是什么样子、做完给我看什么。

## 想先看懂

**带我看懂这个项目**

<Copy id="r-tour" code={`带我看懂这个项目：它是做什么的、怎么在本地跑起来、主要代码在哪。
做好的样子：每一条写明你是从哪个文件看出来的。
做完给我看：一份简短的说明。先只看不改。`} />

「先只看不改」让它只调查。完整做法看[接手一个陌生项目](/howto/new-codebase/)。

**把项目说明写进 AGENTS.md**

<Copy id="r-agents" code={`读这个仓库的文档、代码和 .github/ 里的 workflow，在根目录建一个 AGENTS.md。
我想要：写清用途、怎么装怎么跑、目录结构、CI 会检查什么。
做好的样子：简短，新来的人只看它就能上手。
做完给我看：全文。别的文件不要动。`} />

新对话不记得旧对话，但每次都会读 <Term k="AGENTS.md" />。

## 修 bug

**有报错的 bug**

<Copy id="r-bug" code={`修好 <src/api/users.py> 第 <45> 行的 <TypeError>。
报错原文：<粘贴报错>
应该怎样：<get_user_preferences() 在用户没存偏好时返回默认偏好>
实际怎样：<user.preferences 是 None 时直接崩溃>
做好的样子：<这种情况返回 DEFAULT_PREFERENCES>，原来的测试都通过，再加一个覆盖这种情况的测试。
做完给我看：真正的原因、改了什么、测试结果。`} />

文件、行号、原样的报错、应该怎样和实际怎样，四样都有，它就不用猜。

**上线以后出的事**

<Copy id="r-incident" code={`从 <昨天的部署> 以后，用户登录不了。
现象：<登录表单提交后返回 500>
日志：<Redis connection refused>
可能的原因：<Redis 昨天换了机器，src/config/redis.js 里可能还写着旧地址>
做好的样子：<连新的 Redis（redis.internal:6380）也能正常登录>。
做完给我看：你查到的原因和依据，再给出修法。修之前先等我确认。`} />

把你已经知道的线索都写上，它能少走很多弯路。

## 加功能

<Copy id="r-feature" code={`给 <我们的 Express.js API> 加 <邮箱加密码登录>。
我想要：
1. <POST /api/auth/login 接口>
2. <请求里带邮箱和密码>
3. <对照 PostgreSQL 里的用户校验>
4. <成功返回 JWT，失败返回 401>
照 <src/api/routes.js> 里现有的写法，数据库用 <src/db/index.js> 里的 db.query()。
做好的样子：<用正确的账号调用接口，拿到的 JWT 能通过现有的鉴权中间件>。
做完给我看：改了哪些文件，和你实际调用接口的结果。`} />

点名要照着学的文件，它才知道项目原来是怎么写的。

## 重构

<Copy id="r-refactor" code={`重构 <src/services/user.js> 里的 <UserService>。
要解决的问题：
1. <这个类有 500 多行，拆成几个小的>
2. <数据库查询和业务逻辑混在一起，分开>
不能碰的：公开接口保持不变，别的代码在用它。
做好的样子：功能完全一样，<npm test> 全部通过。
做完给我看：拆成了哪几个部分，和测试结果。`} />

「公开接口保持不变」写明了哪里不能碰。

## 补测试

**写到某个覆盖率为止**

<Copy id="r-coverage" code={`给 <UserService> 补测试。现在覆盖率 <45%>，目标 <85%>。
我想要：先用 <codecov> 找出没覆盖到的代码，再补边界情况的单元测试。每补一批，就重跑一次覆盖率。
做好的样子：覆盖率到 <85%>，全部测试通过。测试发现了 bug，就修代码，不要改测试去迁就。
做完给我看：前后的覆盖率，和你发现的 bug。`} />

**让它做到达标为止：/goal**

<Copy id="r-goal" code={`/goal --max 3 给 <解析器> 补单元测试，并确认全部测试通过`} />

`/goal` 会一轮轮做下去。每轮做完，另一个模型判断目标达到没有，没达到就接着做，最多 `--max` 轮。要后端支持这个命令；它会多调用一个评判模型，花费也会多一些。中途你发一条普通消息，它就停下。

## 先看计划，再让它动手

<Copy id="r-plan" code={`查一下 <PR #123 上失败的 CI>，说清真正的原因，提一个修法。
做好的样子：原因有证据，修法具体到文件。
做完给我看：原因和修法。我批准之前，不要改文件、不要推送、不要在 GitHub 上评论。`} />

它动手太早时，官方的办法就是写明要先等你批准。

## 接着上次做

<Copy id="r-continue" code={`上次你加了 <登录接口>，代码在 <src/api/auth/login.js>。
这次加 <退出登录>：
1. <POST /api/auth/logout 接口>
2. <让当前的 token 失效>
3. <清掉服务端的会话数据>
照登录那部分的写法来。
做好的样子：<退出以后，旧 token 调用接口返回 401>。
做完给我看：改了哪些文件，和你实际调用的结果。`} />

它不记得上次的对话。上次做到哪、代码在哪，要写在第一句里。

## 一天开始，先理一遍待办

<Copy id="r-daily" code={`用已经接好的 GitHub 和 Slack MCP，帮我理一遍今天的事。
我想要它收集：要我处理或审的 PR、分给我的 issue、GitHub 通知和失败的 CI、Slack 里要我回的消息。
做好的样子：按紧急程度分组，每条写标题、为什么要紧、直接链接。
做完给我看：这份清单，最后推荐一件我最该先做的事。没问过我之前，不要改任何东西，也不要发任何消息。`} />

要先在 Customize → MCP Servers 里接好 GitHub 和 Slack。

## 开一个帮手，并行做另一件事

<Copy id="r-child" code={`另开一个代理，去查我其他几个打开的 PR 上失败的 CI 和没处理的审查意见。
我想要：它可以在自己的工作区里改文件、跑测试。
不能做的：推送、合并、在 GitHub 上评论。
做好的样子：每个 PR 都有结论。
做完给我看：每个 PR 的总结和建议的改动。`} />

只把和手上的活不相干的事交出去。它开出来的对话会出现在对话列表里。更多看[同时开好几个对话](/howto/parallel/)。

## 发版前

<Copy id="r-release" code={`准备发版。
我想要：
1. 看一遍上次发版以来的所有改动
2. 查有没有不兼容的 API 改动
3. 确认数据库迁移都能回退
4. 更新 changelog，写发版说明
5. 列出出问题时怎么回滚
做好的样子：每一项都有结论。
做完给我看：发版说明草稿，和你发现的风险。`} />

## 常见的坑

<Q q="一句话交了一大件事，它做着做着就偏了。">
拆开。官方建议一个提示词只做一件事，改动一般不超过 100 行。大活分几步，每一步一个提示词。
</Q>
<Q q="它说做完了，我却不知道算不算做完。">
提示词里没写「做好的样子」。补上一条能检查的：哪些测试要过、哪个接口返回什么。
</Q>
<Q q="还没看计划，它就动手改了。">
写明「我批准之前，不要改文件」。已经改了，就点「Stop」，再让它撤回。
</Q>
