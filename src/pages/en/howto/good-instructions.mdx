## Compare two prompts

With this, it can only guess:

```text
Fix the bug in my code.
```

With this, it knows where to look and what fixed means:

<Copy id="gi-good" title="The clear version" code={`Fix the TypeError in src/api/users.py line 45.
Error message:
TypeError: 'NoneType' object has no attribute 'get'
Expected: get_user_preferences() returns default preferences when the user has none saved.
Actual: it crashes with the error above when user.preferences is None.
What done looks like: it returns DEFAULT_PREFERENCES in that case, and the tests pass.
What to show me when done: what you changed, and the test results.`} />

The difference is a file and line, the exact error, expected versus actual behavior, and a definition of fixed.

## Include four things

- **Where.** File, line, function. If you don't know, name the feature.
- **What happens now, and what should.** Paste errors and logs as they are.
- **Context and limits.** Who uses it, how bad a failure is, what mustn't change, which patterns to follow.
- **What counts as done.** Ideally something a command can check: tests that pass, what an endpoint returns.

<mark>"What counts as done" matters most.</mark> The docs say it does better when success can be checked by a program. Without that, a checklist of what must be finished works too.

| Instead of | Say |
| --- | --- |
| Fix the error | Fix the TypeError on line 45 of api.py |
| Add tests | Add edge-case unit tests for calculateTotal |
| Improve performance | Replace the N+1 queries with one join |
| Clean up the code | Move validation into a ValidatorService class |

## One task at a time

The docs suggest one feature per prompt, usually under 100 lines of change. Split big work into steps, one prompt each. A move to OAuth2, for example, can take three:

<Copy id="gi-phase" title="Step one: analysis only" code={`Analyze the current authentication system and list every touch point that must change for an OAuth2 migration.
What done looks like: each item names its file and its role in the login flow.
What to show me when done: the list. Don't change any code in this step.`} />

Step two adds the OAuth2 configuration and basic token flow, with the old login still working. Step three moves user login over, keeping backward compatibility.

## Use this template

For anything complex, fill this in:

<Copy id="gi-template" title="Task template" code={`## Task
<One sentence on what you want>

## Background
<Why it matters, what this code does, who uses it>

## Requirements
1. <Specific requirement>
2. <Specific requirement>

## Constraints
- <APIs, files, or behavior that must not change>

## Success criteria
- <Which tests pass, which command checks it>

## What to show me when done
- <What changed, test results, screenshots or output>`} />

Give examples when you can. If you want errors in a certain shape, paste one.

## The phrasings that make it drift

- **"Make it look better"**: there's no standard for better. Say what it should look like, or attach a reference.
- **"Figure out what's wrong"**: too vague. Give the symptoms, the errors, and what you've ruled out.
- **"Rewrite everything"**: too big. Pick one piece and do that first.
- **"Do what makes sense"**: it can't know what you want. Write the requirements.
- **Production infrastructure changes with no review**: have a person review first.

The docs also suggest keeping some calls closer to you. These include tasks that need your team's inside knowledge, subjective visual design, and code where no mistake is acceptable.

## You sent it, then noticed it was wrong

- **Stop it.** Select "Stop" next to the message box.
- **Edit and resend.** Select "Branch from here" on your message. The text lands in the message box to edit. The original conversation stays.
- **It got somewhere good, and you want a different next step.** Select "Branch from here" on its reply. The new conversation picks up from there.

Branching needs a local <Term k="Agent Server" /> backend that supports conversation forks. Without the button, start a new <Term k="对话" /> and put the earlier conclusions in your first message.

## Write repeated instructions into AGENTS.md

The second time you type the same instruction, put it in <Term k="AGENTS.md" /> at the project root. Every conversation reads it at the start:

```markdown
## Things OpenHands should know

- When adding API endpoints, always add them to routes/index.js
- Our date format is ISO 8601 everywhere
- All database queries go through the repository pattern
```

## Check before you send

Send it." />

## Stuck?

<Q q="It asked a pile of questions before starting.">
That's normal. Answer them, then let it start. Next time, put those answers in your first message.
</Q>
<Q q="It changed far more than I asked for.">
Set the scope explicitly: "Only change this one file." "Don't touch other features." The docs list time and scope limits among the constraints to state.
</Q>
<Q q="It never knows the project's conventions.">
It doesn't remember earlier conversations. Put the conventions in AGENTS.md, which every conversation reads.
</Q>
