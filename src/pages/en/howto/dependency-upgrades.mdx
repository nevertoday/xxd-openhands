## Major versions: check compatibility, then fix one spot at a time

Major versions often break things. The docs count framework and major dependency upgrades as complex tasks, best split into smaller pieces.

**Step one: find out what you'll hit.**

<Copy id="du-compat" title="Check compatibility first" code={`Check compatibility for upgrading React from 16 to 18.
What I want:
1. Find deprecated React patterns in our code
2. List all components using lifecycle methods
3. Find any use of string refs or findDOMNode
4. Check whether our third-party libraries support React 18
5. Estimate the effort
What done looks like: a list where every item names its file.
What to show me when done: the list, and which third-party libraries also need a major upgrade. Read only for now.`} />

**Step two: work through the list.**

<Copy id="du-major" title="Handle breaking changes" code={`Upgrade axios from v0.x to v1.x and handle the breaking changes.
What I want:
1. List every breaking change in the axios 1.0 changelog
2. Find every place our code uses axios
3. For each one: show the current code, the updated code, and why it changed
4. Make one commit per logical change
What done looks like: all tests pass.
What to show me when done: the list of commits, with an explanation of each change.`} />

"One commit per logical change" means that if one step causes trouble, you can roll back just that step.

When several packages move together, such as react, react-dom, and react-router-dom, give it every current and target version. Have it work out the order before it changes anything.

## Afterward, have it check everything

<Copy id="du-check" title="Check after upgrading" code={`The dependency upgrades are done. Validate the application.
What I want:
1. Run the full test suite (unit, integration, end-to-end)
2. Confirm test coverage hasn't dropped
3. Run type checking, if the project has it
4. Run linting with the new rule versions
5. Build the application for production
What done looks like: all of the above pass.
What to show me when done: the result of each step, and your analysis of anything that failed.`} />

## Check every week automatically

Send this in a new conversation and it sets up an <Term k="自动化" /> for you:

<Copy id="du-auto" title="Weekly dependency check" code={`Create an automation called "Dependency Checker" that runs every Monday at 8 AM.
What I want it to do each time:
1. Scan all package.json and requirements.txt files
2. Check for outdated dependencies
3. Write a report listing packages with available updates, grouped by major, minor, and patch
4. Post the report to the #engineering Slack channel
What done looks like: the automation exists and is enabled.
What to show me when done: its name, its schedule, and what it does each run.`} />

Step 4 needs Slack connected. If it isn't, drop step 4. Each report then stays in the conversation the automation starts, which you'll find in the conversation list. For managing automations, see [full guide step 6](/en/guide/6-automations/).

## Stuck?

<Q q="After upgrading, a pile of tests failed.">
Roll back and upgrade one major-version package at a time. Use the compatibility check above to list the problems first, then fix them one by one.
</Q>
<Q q="/codereview won't approve my upgrade PR because the version is too new.">
The code-review skill won't approve a third-party version published less than 7 days ago. Wait a few days and ask again, or make the call yourself.
</Q>
<Q q="The weekly report never shows up in Slack.">
Check that the Slack bot is installed in the workspace and invited to #engineering. The bot can't read channels it hasn't joined.
</Q>
